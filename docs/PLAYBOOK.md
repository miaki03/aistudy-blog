# 教材生产方法论

> 学科无关。把任何领域的知识，做成一套**能在网页上逐节自学、可验收、不漂移**的教材。
> 实例：ARG / CTF / Puzzle Hunt 课程（29 章 / 111 节 / 8 个项目）。
> 换成高等数学、日语语法、乐理、Linux 运维，骨架不变，只换内容与校验手段。
>
> **读者对象：接手任务的 AI agent，或想自己复刻的人。这份文档不给教材的读者看，不上线。**

---

## 0. 先判断这个学科适不适合

这套方法不是万能的。开工前用三问筛一遍：

| 问 | 为什么必要 | 不满足会怎样 |
| --- | --- | --- |
| 有没有**可核对的中间结果**？ | 每节要一个「读者做完能看到的具体结果」开场 | 只能写散文，变成科普而不是教材 |
| 有没有一批**可反复施加深度的样本**？ | 用来防脱节、防漂移、当回归测试 | 每章自造例子，学完互不相干 |
| 有没有**稳定可查的表**？ | 速查表是「减少搜索依赖」的载体 | 读者每节都要出去查，链式依赖断裂 |

三问全过 → 可以。过两个 → 可以，但要把缺的那项补出来（数学没有天然样本，就固定一组「麻烦函数」）。
只过一个 → 别用这套，写成专题长文更合适。

**已验证适配**：安全/CTF、高等数学、编程语言、语言语法、工具操作、乐理。
**需要改造**：纯审美类（作品评析）——「可核对结果」要换成「可对照的判定标准」。

## 1. 全书结构：三层

```
Part（能力阶层，3–7 个） → 章/单元（验收单位，20–30 个） → 节（交付原子，15–25 分钟）
```

比例经验值：1 个 Part ≈ 3–5 章；1 章 ≈ 3–5 节；全书 ≈ 100 节 ≈ 60–70 学时。

### 1.1 节 = 交付原子

**这是全套方法里最重要的一条。** 它同时解决三个问题：一次会话能产出、读者每次都有闭环、漂移能当场发现。

每节固定四件套，顺序不许换：

| 件 | 要求 | 反例 |
| --- | --- | --- |
| **锚点结果** | 可核对的具体结果：命令行会话（输入+输出）、算出来的数、能跑的代码、可对照的判定 | 先给三段定义再给例子 |
| **机制** | 为什么是这个结果，推导不跳步，**不用比喻代替解释** | 「就像……一样」 |
| **速查** | 本节用到的表**就地给**；没有就写「本节无新表」 | 指向文末附录 |
| **题** | 1–2 题，编号 `<章>.<节>-<序号>` | 章末一次性堆 6 题 |

**为什么速查必须在节内**：放文末附录等于要求读者先背再用。参考 C++ Primer——`表 3.1` 就出现在第一次用 `string` 操作的那一页。

### 1.2 章 = 验收单位

- **章首**：**一条**主目标（可带 1–2 个子句），形式是「给定 X 能做出 Y」。
- **章末**：术语表（本章的，不集中到全书）+ 自检 3 题 + 动手 1–2 个。

**两级练习**（对应 C Primer Plus 的 Review Questions / Programming Exercises）：

| 层 | 数量 | 性质 |
| --- | --- | --- |
| 自检 | 3 | 概念层，一问一答，尽量机器可验 |
| 动手 | 1–2 | 要交出东西（表格、脚本、报告、推导），可人工判 |

> **为什么主目标只许一条**：三条目标本身就是堆料的接口。写满三条等于承诺三个能力，80 分钟装不下，结果每条都只是"提了一句"。一章只承诺一件事，其余拆成下一章。

### 1.3 Part = 能力阶层

- Part 开头一句「学完能独立完成什么」（不是"了解 X"）
- Part 末尾一个**项目**：一次完整循环，有交付物和时间上限

项目不是"练手"，是**回归测试**：项目做不出来 = 这个 Part 的章有问题，回头改章，不往前写。

## 2. 章的三条准入判据

不满足就别写这一章。

| 判据 | 怎么查 | 不满足怎么办 |
| --- | --- | --- |
| 能出**换外壳的变式题** | 同一原理换个外表，读者还认得出吗 | 说明只在背名词，砍或并入别章 |
| 能被 **≥3 处后续复用** | 列出具体章号，写不出就是凑数 | 降级为某一章的「速查」小节 |
| 有**可核对的锚点结果** | 每节第一段能不能写出具体结果 | 这节不该存在 |
| **论证不依赖未教的概念** | 本章的核心结论，用到了后面某章才讲的东西吗 | 换论证骨架，或把那个概念提前 |

第四条是真实踩过的：某章的目标是「说明为什么一个字节写成两位十六进制」，而它的论证骨架是「1 字节 = 8 个二进制位 = 4 + 4」——**二进制位在四章之后才教**。结果是读者能把结论背下来，但验不了，复验原话是「背得出、说不清」。

换骨架后解决：不靠二进制位，而靠**范围比较**——一个字节表示 0–255 共 256 个数；两位十六进制有 16 × 16 = 256 种，正好覆盖。这个读者能自己用乘法验。

第二条是对抗「堆积知识」最有效的机制：**不能复用的知识 = 不参与解决问题 = 不该当课**。
它砍起来很狠，但这就是价值。曾有一版 50 页的方案，被这一条砍掉一半。

## 3. 让「学过」变成「会」：三个装置

教材失败的典型方式不是写错，是**每章都对、合起来读者什么也不会**。

### 3.1 贯穿样本（Running corpus）

选一批**永不改动**的样本文件/数据/题目，从第一个 Part 用到最后一个，每次施加更深的手段。
C++ Primer 用 `SalesItem` 从第 1 章用到第 14 章，就是这个意思。

| 作用 | 说明 |
| --- | --- |
| 防漂移 | 后面的章若推翻前面章的结论，当场暴露，不用等评审 |
| 有实物 | 读者的产出是"这批文件上的档案逐层变厚"，不是"又读完一页" |
| 省重复 | 每章不重造例子 |

**必须确定性生成**：写 `build-corpus` 脚本，固定随机种子，重复运行产出同一批字节。否则样本一变，"推翻旧结论"的信号就假了。
**必须机器核对**：再写 `verify-corpus` 脚本，逐条断言"样本里确实藏着该藏的东西"。这份脚本同时就是答案键。

学科适配示例：

| 学科 | 贯穿样本 |
| --- | --- |
| 安全/CTF | 7 个故意做脏的样本（改过头的图片、伪加密压缩包、带垃圾前缀的流、传 base64 的抓包） |
| 高等数学 | 一组「麻烦函数」：在 0 附近震荡的、不可导的、条件收敛的、要不同变形的 |
| 编程语言 | 一个逐步重构的小程序，每章加一个语言特性 |
| 日语 | 一段逐章加语法点的日记，每章回读一遍 |
| 乐理 | 一首逐章加深分析的曲子 |

### 3.2 概念台账（Concept ledger）

一个 JSON 文件登记**每个概念**：id、中英文、**首次定义章**。

三条规则：

1. 新章只能引用**已登记**的概念，或自己定义并登记；
2. 一个概念只能有一个首次定义章；
3. 改已发布章的术语 → 必须记变更并列受影响章（**语义冻结**）。

**这是唯一能自动发现漂移的机制**：写到第 10 章时引用了一个台账里没有的概念，脚本立刻报错。人工评审只能抽查，台账是全覆盖的。

反例（真实发生过）：台账记某概念由 A 章定义，但 A 章重写后不再声明它——脚本立刻报"台账与页面不一致"。这类错误人眼几乎抓不到。

### 3.3 复用矩阵

一张表：每个章 → 被哪几个章/项目复用。写大纲时就填，写正文时核对。
它把"我认为这章重要"变成"这章被这 6 处用到"。填不出来的章，删。

## 4. 三方分工：最小充分上下文

### 4.1 问题

作者如果带着「整段对话记忆」写，会稳定地犯四个错：

| 错 | 表现 |
| --- | --- |
| 跳步 | 「这正是前面讲过的……」——作者记得，读者不记得 |
| 用内部坐标 | 「这是 Part 2 的内容」「W5 再学」——那是进度表，不是读者的坐标系 |
| 替读者补全 | 「显然要先 xxd 再 cat」——作者知道后果，读者不知道 |
| 用历史当理由 | 「上一版这里做错过」——读者没有那个上一版 |

反过来，**只给一个空洞题目也不行**：写作 agent 不知道前后有什么章、哪些概念已定义过，就会自己发明顺序、重复讲别章内容、把后面的坑提前踩。**那比跳步更严重。**

### 4.2 所以

**给全「计划与位置」，不给「历史与讨论」。**

这不是"盲写"——是**最小充分上下文**。上下文少 ≠ 信息少。

| 角色 | 谁 | 看到什么 | 产出 |
| --- | --- | --- | --- |
| **校验方** | 主 agent | 全部上下文 | 写作包、实测数据、题库与 verify、终审、发布 |
| **写作方** | 子 agent | 只有写作包 12 项 | 正文草稿 + 交稿自查 |
| **复验方** | 另一个子 agent | 只有读者画像 + 正文 | 卡点清单（不许提建议） |

写作方知道计划，不知道历史；复验方什么都不知道，只有正文——它最接近真实读者。

**实测证据**（第一章）：写作方自查报出 5 条跳步；独立复验报出 15 条卡点，其中包含**一处事实错误**（"那 9 个点是 9 个不同的字节"，实际同一行里 `0d` 出现两次、`00` 三次），并直接判定「文章开头承诺的事做不到」。
这 20 条里有相当一部分，是带着上下文写的人**必然看不出**的——因为它们不是错，是"作者已经知道所以不写"。

## 5. 写作包：12 项

| # | 项 | 要求 |
| --- | --- | --- |
| 1 | **书籍定位与读者画像** | 一段话：给谁、现有基础边界、外部约束（单人 / 不查外网 / 英文弱 / 用什么系统） |
| 2 | **全局大纲** | 全部 Part 与章清单，每章一句目标。**必须给**，否则会重复别章内容 |
| 3 | **本章位置** | 读者读到这里已经会什么：前置章号 + 已定义概念清单 |
| 4 | **本章唯一目标** | 一句话，可测：「给定 X 能做出 Y」。不允许「理解 Z」 |
| 5 | **节表 + 实测跑通物** | 每节：锚点结果（命令 + **真实输出**，由校验方跑过）+ 机制一句话 + 速查内容 + 题号 |
| 6 | **风格规范全文** | 照抄，不要摘要 |
| 7 | **概念边界** | 可引用的（已定义）+ 本章允许新增的（给 id / 中文 / 英文） |
| 8 | **明确不教** | 列出容易顺手写进来的邻近主题，并指明属于哪一章 |
| 9 | **题目与 verify** | 考点、编号、机验方式由校验方给；写作方写题面与折叠提示/答案 |
| 10 | **篇幅参考** | 字数区间，并注明**是参考不是门槛**（见 §7） |
| 11 | **交付格式** | front matter 模板，字段名与取值照抄 |
| 12 | **交稿自查** | 要求逐节回答「读者可能卡在哪」，并列出自己拿不准的地方 |

**明确不给的**：讨论过哪些方案、为什么砍掉、旧版本长什么样、别章正文、偏好怎么演化的、任何进度元话语（「Part 2 会讲」）。

**判据**：一段信息如果只解释「为什么变成现在这样」，而不影响「这一章要写成什么样」，就不给。

## 6. 复验协议

复验方是**独立子 agent**，输入只有：读者画像 + 本章正文。不给写作包、不给大纲、不给 specs。

**唯一任务**：从头读到尾，逐节标出

1. **我必须跳出去查**——文章要求我知道它没解释的东西；
2. **我必须猜**——给了结论，但我无法验证，只能先信；
3. **我没法确认自己理解得对不对**。

约束：

- **不许提修改建议**。一提建议就变成第二个作者，会把自己的写法混进来；
- 按「卡住程度」排序，不按章节顺序；
- 允许说「这一节我全看懂了」——那是有用信号；
- 它读不懂时**不要作者去解释**。读不懂就是读者读不懂。

**为什么必须独立**：有记忆的人会下意识用脑内上下文补全跳步，看不出问题。这不是能力问题，是必然。

**必须问的收尾问题**：「读完之后，你能做到文章开头承诺的那件事吗？」——
这一问会把"局部都看懂了，但整体做不到"暴露出来。首次实测就是靠这一问发现：读者卡在"该打开哪个终端"，所有命令都还没开始。

**通过线建议**：卡点全部消掉，或在 `specs/` 里"已记录且接受"并写明理由。后者必须书面留痕，否则等于没做。

## 7. 篇幅：参考值，不是门槛

字数区间的作用是**预警**，不是硬拆依据。

> 像设计函数：不能因为一条必要的代码让函数超过 30 行，就把它硬拆成两个函数。拆开的代价是读者要在两个地方拼回一个概念。

规则：

- 超上限时**不自动拆章**，先问「这段超出是不是必要」；
- 必要时保留，并在 `specs/<章>.md` 写明超出理由；
- 不必要时才砍，砍的优先顺序：**删元话语 > 删重复示例 > 删铺垫 > 合并节**；
- 低于下限也要警惕：可能该讲清的机制没讲。

判断「必要」的唯一标准：**删掉它，读者下一步就做不出来。** 不是「它很重要」，是「删了会卡」。

## 8. 练习站优先：手熟型知识不自己造练习

| 类型 | 判据 | 做法 |
| --- | --- | --- |
| **手熟型** | 知道怎么做之后，剩下的是练多少遍 | 指向成熟免费练习站，正文只给最短必要知识 + 指引 |
| **结构化型** | 不解释就做不出来（判据、对照表、推导） | 自己写 |

常备站点：

| 站点 | 覆盖 | 免费 |
| --- | --- | --- |
| OverTheWire: Bandit | 终端基础到中级（`ls`/`cat`/`file`/`grep`/`sort`/`uniq`/`tr`/`base64`/`tar`/`ssh`/权限/定时任务） | 是，SSH 直连，免注册 |
| OverTheWire: Natas | Web 入门（源码泄露、目录遍历、注入启蒙） | 是 |
| picoCTF | CTF 入门题，按方向分类 | 是，需注册 |
| CryptoHack | 密码学（古典与现代） | 是，需注册 |
| 各年度公开 Puzzle Hunt 归档 | Puzzle Hunt 真题 | 是 |

### 引用练习站必须写清的四件事

1. **打哪几关**（具体编号，不是「做完 Bandit」）；
2. **为什么是这几关**（对应本章哪个目标）；
3. **命令解释**（练习站通常只给线索，不给解释）；
4. **它缺什么**（见下）。

### 练习站普遍缺的四样，必须由正文补

| 缺什么 | 怎么补 |
| --- | --- |
| **成体系的任务流** | 关卡式推进每关一个孤立技巧，没有「给一份日志 → 产出一份报告」的整条流程 |
| **排错** | 几乎不教「报错在说什么」。必须自己写 |
| **中文** | 全是英文且大量用双关。把提示翻成直白的话，但**不替读者把关做掉** |
| **为什么** | 只给「怎么做」，不给「为什么是这个而不是那个」。判据与对照表自己写 |

> **注意练习站的反作用**：它是全英文的，"去打这几关"对英文弱的读者本身就是一次跳出去查。
> 所以指引里必须写清**怎么进去**（哪一行命令、照抄哪里），并且明确「卡住就跳过，本章只要求把这几个命令用熟」。

## 9. 可验证性工程

**一门教材的可信度，取决于它的断言有多少能被复跑验证。**

### 9.1 断言分级

| 级 | 判据 | 处理 |
| --- | --- | --- |
| A 机器可验 | 一条命令/一段代码能复算出答案 | 必须登记 `verify`，每次提交跑一遍 |
| B 证据可核 | 不能自动算，但人能按写明的步骤核对 | 标 `manual`，写具体 `evidence`（"看第 3 行"可以，"自己验证一下"不行） |
| C 只能人判 | 主观判断 | 尽量改写成 B；改不了就别当结论写进正文 |

**默认目标是把题推向 A。** 目标占比 ≥70%。

### 9.2 题库格式（最小可用）

```json
{
  "id": "U00.2-01",
  "page": "u00-see-bytes",
  "skills": ["xxd"],
  "difficulty": 1,
  "minutes": 3,
  "answer": "89504e47",
  "verify": "xxd -l 4 -p static/samples/S-01.png"
}
```

校验脚本跑 `verify`，把 stdout 与 `answer` 比对，不一致就报错。
好处：**正文和答案键不可能不一致**——正文写错了，脚本会拦住。

### 9.3 verify 命令的坑（都真实踩过）

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **shell 不是 bash** | `verify` 在 `/bin/sh`（dash）里跑，`printf '\x89'` 不解释转义，`file` 报 `ASCII text` 而不是 `data` | 要生成二进制内容，一律 `python3 -c "open(p,'wb').write(b'...')"`，不依赖 shell 转义 |
| **相对路径依赖 cwd** | 换个目录跑就找不到样本 | 统一从仓库根目录跑；或脚本内 chdir |
| **答案含空格/中文** | stdout 与 answer 差一个空格就失败 | 答案写成单一可打印行；必要时在 verify 里 `awk` 重排 |

### 9.4 学科适配：怎么把题变成可机验

| 学科 | 做法 |
| --- | --- |
| 安全/CTF | 直接跑命令，比对输出 |
| 数学 | `sympy` 化简/求值后比对；无解析解用 `mpmath` 高精度数值 + 写出误差界 |
| 物理 | 量纲检查 + 特殊值代入 + 数值解 |
| 编程 | 跑测试用例 |
| 语言 | 固定语料上的标注一致性检查；或自评量表 + 抽查 |
| 乐理 | MIDI/音频特征值（音高、和弦识别）比对 |

数学特别注意：**别只验最终答案**。中间步骤也要给可核对的值（某一步的导数、某个代换后的积分），否则读者错了不知道错在哪。

## 10. 生产流水线

### 10.1 三级节奏

| 级 | 单位 | 产出 | 评审 |
| --- | --- | --- | --- |
| 节 | 15–25 分钟 | 一节正文 + 题号登记 | 自查 |
| 章 | 3–5 节 | 章首 1 条主目标、章末术语表 + 自检 + 动手 | 校验脚本全绿 + **独立复验** + 提交 |
| Part | 3–5 章 + 1 项目 | 项目交付物 | 一次人工评审 + 用户验收 |

章级只跑脚本，人眼留到 Part 级——因为 Part 末的项目会把前面章的漏洞一次性暴露。

### 10.2 开写前的 5 分钟：节表

不写长篇大纲，写一张表：

```markdown
| 节 | 锚点结果（读者做完会看到什么） | 机制一句话 | 速查 | 题 |
| --- | --- | --- | --- | --- |
| 0.1 | `pwd` 输出路径，`ls` 列出条目 | 命令 = 名字 + 参数 | 4 条命令表 | U00.1-01 |
| 0.2 | `xxd -l 16` 吐出 8950 4e47… | 三列：偏移 / 字节 / 可打印 | xxd 参数 | U00.2-01 |
```

**这张表是漂移的第一个拦截点**：某节的锚点结果写不出来，说明它没有可教的动作，当场删或并。5 分钟投入，省一次返工。

### 10.3 逐节写作

1. 按四件套顺序写（锚点 → 机制 → 速查 → 题）；
2. **边写边跑**：写完一条命令立刻执行，把真实输出贴进去，不构造；
3. 题先登记到题库，再写折叠提示与答案；
4. 一节写完立刻提交（`feat(U00.2): …`）。

### 10.4 校验脚本「随用生长」

**不要一开始写一堆检查项。** 检查项跟着课程长：

| 写到 | 才加上的检查 |
| --- | --- |
| 第 1 章 | 概念是否在台账登记；front matter 字段齐全 |
| 第 2 章 | 题号与题库双向一致；每条 `verify` 跑通 |
| 第 3 章 | 复用点 ≥3 |
| 第一个项目 | 项目覆盖：该 Part 的每章都被项目引用 |

脱离用例写的校验，一定过度设计。曾有一版预先写了 4 个脚本，一半日后用不上。

## 11. 防漂移：六条结构约束

比"多加评审环节"有效得多。评审只能事后抓，结构约束能事前禁。

| # | 约束 | 拦什么 |
| --- | --- | --- |
| 1 | **节表前置**：锚点结果写不出来就不写这节 | 没有可教动作的空节 |
| 2 | **概念台账**：只能引用已登记概念 | 语义被偷偷改 |
| 3 | **语义冻结**：已提交章的定义不改，只追加 | 前后章冲突 |
| 4 | **复用门槛**：章 ≥3 处复用，否则降为速查 | 知识堆积 |
| 5 | **贯穿样本**：新章若推翻旧章结论，立即暴露 | 理解被后续否定而没人发现 |
| 6 | **项目即回归测试**：项目做不出来就回头改章 | 一路往前写，越写越虚 |

**逐节产出时，漂移只可能发生在两个地方**：概念语义被偷改、依赖被凭空加。约束 2 和 3 正好各封一个。

## 12. 交付与发布纪律

### 12.1 构建配额

静态站托管（Cloudflare Pages / Vercel / Netlify）每次推送都触发一次构建，免费额度按次计。

- **commit 密，push 稀**；
- **绝不**把 `git commit` 和 `git push` 写在同一条命令里；
- **push 前单独取得当次确认**。「批准了内容变更」≠「批准推送」——这是两个决定；
- 任何改变**线上可见内容**的动作（下线页面、改导航、改标题）都单独确认；
- 推送前先在本地跑生产构建，**不拿云端构建当调试手段**。

### 12.2 在线与离线的边界

| 目录 | 是否上线 | 内容 |
| --- | --- | --- |
| `content/` | ✅ | 教材正文 |
| `static/samples/` | ✅ | 贯穿样本，读者要下载 |
| `docs/` | ❌ | 方法论、决策记录、进度、评审 |
| `specs/` | ❌ | 节表与实测记录 |
| `kb/` | ❌ | 题库与概念台账 |

**这条边界要写进 agent 的规则里，不能靠记性。**

真实事故：把内部方法论当成文章发布、还加进了导航栏——读者看到的是"这门课怎么造出来的"，毫无用处；撤销要删页面、删导航、再把被挪走的原件搬回去。

### 12.3 验收要看「能不能走到」

发布后不要只验证「文件生成了」「URL 能打开」，要验证**从首页能否一步走到新页**。

真实事故：六章发布成功、URL 全通，但首页的列表源只含旧的 section，导致所有新章没有入口——用户看到的是"没更新"。
这是**索引与内容不同源**的典型失败：内容层正确，导航层漏了。

### 12.4 两套体系不能并存

旧版内容不下线，会和新结构同时挂在站上（例如旧的"16 周 W 系列"和新的"Part/章结构"）。
读者不知道信哪个，而在正文里写一句"以本页为准"**不是解决方案**——那是用一句声明去掩盖两套并存。

正确做法：旧内容显式下线（转草稿 / 移入归档区 / 加废弃横幅），并且**只保留一种编号体系**。

## 13. 常见失败模式

| 失败模式 | 症状 | 拦它的约束 |
| --- | --- | --- |
| **分类学冒充课程** | 按学科分支排章，读者学完不会用 | §1.3 项目当回归测试 |
| **知识堆积** | 每章都对，合起来不会；删掉一半不影响能力 | §2 复用门槛 |
| **无螺旋** | 同一概念换个外壳读者就认不出 | §3.1 贯穿样本 |
| **前置是假的** | 依赖边只是"主题相邻"，不是"缺了它第一步就做不下去" | §10.2 节表前置 |
| **章太大** | 一章 2 小时，读者永远没有闭环感 | §1.1 节 15–25 分钟 |
| **三目标章** | 章首列 3 条目标，等于承诺 3 个能力，每条都提了一句 | §1.2 主目标只许一条 |
| **断言靠猜** | 报错原文、数值、字节数看起来合理但是编的 | §9 完整会话 + 边写边跑 |
| **自己复验** | 作者读自己的稿子，用脑内上下文补全了所有跳步 | §6 独立复验 |
| **元话语泄漏** | 「Part 2 会讲」「W5 再学」——进度表混进正文 | §5 不给什么 |
| **两套体系并存** | 旧内容没下线，和新结构同时挂在站上 | §12.4 |
| **校验过度设计** | 一开始写 4 个检查脚本，一半日后用不上 | §10.4 随用生长 |
| **常识当课上** | 查表内容单独成章，占掉注意力却不训练动作 | §2 复用门槛 |
| **靠声明掩盖冲突** | 正文写一句"以本页为准"，实际两套结构都在 | §12.4 |
| **只验文件不验入口** | 页面生成了、URL 通了，但首页没有链接 | §12.3 |

## 14. 从零复刻：12 步

以新建一门「高等数学」教材站为例。

```text
1.  用三问（§0）确认学科适配
2.  定 Part 划分：能力阶层，3–7 个，每个一句「学完能独立完成什么」
3.  定章清单：20–30 章，每章填「复用点」列——填不出来的删
4.  选贯穿样本：一组固定函数/数据，写 build-corpus 与 verify-corpus
5.  建最小题库骨架：id / page / answer / verify
6.  写第 1 章的节表（5 分钟那张表）
7.  准备写作包 12 项（§5），交给写作 agent
8.  它交稿后，交给另一个 agent 做独立复验（§6），按卡点改
9.  校验脚本按 §10.4 长到"够用"，不多写
10. 写第 1 个 Part 的项目页，用它当回归测试
11. 之后按 §10 量产：节提交、章评审、Part 收尾才推送
12. 全部完成后补：索引页（自动生成学习顺序）、免责与来源页
```

前 6 步做完再动笔写正文。**顺序错了就会返工**——第 7 步才发现第 3 步的章划分不对，代价是重写整章。

## 15. 学科适配对照

| 通用概念 | CTF / Puzzle Hunt 实例 | 高等数学实例 |
| --- | --- | --- |
| 节 | 「0.2 用 xxd 看见字节」 | 「0.3 极限存在的两个充分条件」 |
| 锚点结果 | 终端会话（`$` + 命令 + 真实输出） | `sympy.limit(...)` 算出值，并给代入路径 |
| 贯穿样本 | 7 个做脏的样本文件 | 一组「麻烦函数」，反复求导/积分/展开/判敛 |
| 速查 | 头字节表、掩码表，就地放 | 导数表、积分表、等价无穷小，就地放 |
| 自检（机器可验） | 跑命令比对输出 | 算一个定积分，`sympy.integrate` 比对 |
| 动手 | 写脚本产出一份报告 | 推一段证明，人工判 |
| 复用门槛 | 「Python 读二进制」须被 ≥3 章用到 | 「换元法」须被 ≥3 章用到，否则不单独成章 |
| 项目 | 「用四种编码剥一层套娃」 | 「用三种方法算同一个积分并比较误差」 |

## 16. 一页速记

```text
三层：Part（能力）→ 章（验收）→ 节（15-25 分钟交付）

每节四件套：锚点结果 / 机制 / 速查 / 题
每章：1 条主目标 + 术语表 + 自检 3 + 动手 1-2
每 Part：一句能力 + 一个项目（当回归测试）

三条准入：能出换壳变式题 / ≥3 处复用 / 有可核锚点
三个装置：贯穿样本 / 概念台账 / 复用矩阵
三种标记：易错 / 约定 / 实践

三方分工：校验（有全部上下文）→ 写作（只有写作包）→ 复验（只有正文）
写作包 12 项：定位 / 大纲 / 前置 / 唯一目标 / 节表与实测输出 / 风格 /
              概念边界 / 不教 / 题目与考点 / 篇幅参考 / 交付格式 / 自查要求

篇幅是预警不是门槛：删了会卡才保留。
手熟型知识给练习站 + 指引；结构化知识自己写。
练习站缺的四样必须补：任务流 / 排错 / 中文 / 为什么。

防漂移六条：节表前置 / 概念台账 / 语义冻结 / 复用门槛 / 贯穿样本 / 项目回归
发布纪律：commit 与 push 分开；push 单独确认；上线前验「首页能否走到」

开写前 5 分钟写节表，写不出锚点就删这节。
校验收紧随用生长，不想象需求。
复验必问收尾一问：「读完后你能做到开头承诺的事吗？」
```
