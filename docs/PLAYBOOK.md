# PLAYBOOK · 用博客复刻一本自学教材

> 这份文档与具体学科无关。它描述的是**如何把一个领域的知识，做成一套能在网页上逐节自学、可验收、不漂移的教材**。
> 本仓库（ARG/CTF/Puzzle Hunt）是它的一个实例。换成高等数学、线性代数、日语语法、乐理、Linux 运维，骨架不变，只换内容与校验手段。
>
> 读者对象：接手这个任务的 AI agent，或想自己复刻的人。

---

## 0. 先判断这个学科适不适合

这种形式**不是万能的**。开工前用三问筛一遍：

| 问 | 为什么必要 | 不满足会怎样 |
| --- | --- | --- |
| 有没有**可核对的中间结果**？ | 每节都要以一个「读者敲完/算完能看到的具体结果」开场 | 只能写散文，变成科普而不是教材 |
| 有没有一批**可反复施加深度的样本**？ | 用来防脱节、防漂移、当回归测试 | 每章自造例子，学完互不相干 |
| 有没有**稳定可查的表**？ | 速查表是「减少搜索依赖」的载体 | 读者每节都要出去查，链式依赖断裂 |

三问全过 → 可以。过两个 → 可以，但要把缺的那项补出来（例如数学没有"样本"，就固定一组「麻烦函数」）。
只过一个 → 别用这套，写成专题长文更合适。

**已经验证适配**：CTF/安全、高等数学、编程语言、语言语法、工具操作。
**需要改造的**：纯审美类（作品评析）——「可核对结果」要换成「可对照的判定标准」。

## 1. 三层结构（整套方法的地基）

```
Part（能力阶层，3–7 个）   →   章/单元（验收单位，20–30 个）   →   节（交付原子，15–25 分钟）
```

比例经验值：1 个 Part ≈ 3–5 章；1 章 ≈ 3–5 节；全书 ≈ 100 节 ≈ 60–70 学时。

### 1.1 节 = 交付原子

**这是全套方法里最重要的一条。** 它同时解决三个问题：一次会话能产出、读者每次都有闭环、漂移能当场发现。

每节固定四件套，顺序不许换：

| 件 | 要求 | 反例 |
| --- | --- | --- |
| **锚点结果** | 一个可核对的具体结果：命令行会话（输入+输出）、一个算出来的数、一段能跑的代码、一个可对照的判定 | 先给三段定义再给例子 |
| **机制** | 这个结果为什么是这样，推导不跳步，**不用比喻代替解释** | 「就像……一样」 |
| **速查** | 本节用到的表**就地给**；没有就写「本节无新表」 | 指向文末附录 |
| **题** | 1–2 题，编号 `<章>.<节>-<序号>` | 章末一次性堆 6 题 |

**为什么「速查」必须在节内**：放在文末附录，等于要求读者先背再用。参考 C++ Primer 的做法——`表 3.1` 就出现在第一次用 `string` 操作的那一页。

### 1.2 章 = 验收单位

章首、章末各固定几件：

- **章首**：3 条「读完能做什么」，动词开头，必须可测（写「理解 X」不合格，写「给定 Y 能做出 Z」合格）
- **章末**：术语表（本章的，不集中到全书）+ 自检 3 题 + 动手 1–2 个

**两级练习**（对应 C Primer Plus 的 Review Questions / Programming Exercises）：

| 层 | 数量 | 性质 |
| --- | --- | --- |
| 自检 | 3 | 概念层，一问一答，**尽量机器可验** |
| 动手 | 1–2 | 要交出东西（表格、脚本、报告、推导），可人工判 |

### 1.3 Part = 能力阶层

- Part 开头一句「学完能独立完成什么」（不是"了解 X"）
- Part 末尾一个**项目**：一次完整循环，有交付物和时间上限

项目不是"练手"，是**回归测试**：项目做不出来 = 这个 Part 的章有问题，回头改章，不往前写。

### 1.4 章的三条准入判据（不满足就别写）

| 判据 | 怎么查 | 不满足怎么办 |
| --- | --- | --- |
| 能出**换外壳的变式题** | 同一原理换个外表，读者还能认出来吗 | 说明这章只是在背名词，砍或并入别章 |
| 能被 **≥3 处后续复用** | 列具体章 ID，写不出来就是凑数 | 降级为某一章的「速查」小节，不单独成课 |
| 有**可核对的锚点结果** | 每节第一段能不能写出具体结果 | 这节不该存在 |

第二条是对抗「堆积知识」最有效的一招：**不能复用的知识 = 不参与解决问题 = 不该当课**。它砍起来很狠，但这就是它的价值。

## 2. 让「学过」变成「会」的三个装置

教材失败的典型方式不是写错，是**每章都对，合起来读者什么也不会**。三个装置专门治这个。

### 2.1 贯穿样本（Running corpus）

选一批**永不改动**的样本文件/数据/题目，从第 1 个 Part 用到最后，每次施加更深的手段。

C++ Primer 用 `SalesItem` 这个类从第 1 章用到第 14 章，就是这个意思。

| 作用 | 说明 |
| --- | --- |
| 防漂移 | 后面的章若推翻了前面章的结论，当场暴露，不用等评审 |
| 有实物 | 读者的产出是"这批文件上的档案逐层变厚"，不是"又读完一页" |
| 省重复 | 每章不重造例子 |

**必须确定性生成**：写一个 `build-corpus` 脚本，固定随机种子，重复运行产出同一批字节。否则样本一变，"推翻旧结论"的信号就假了。
**必须机器核对**：再写一个 `verify-corpus` 脚本，逐条断言"样本里确实藏着该藏的东西"。这份脚本同时就是答案键。

学科适配示例：

| 学科 | 贯穿样本 |
| --- | --- |
| 安全/CTF | 7 个故意做脏的样本文件（改过头的图片、伪加密压缩包、带垃圾前缀的流） |
| 高等数学 | 一组「麻烦函数」：在 0 附近震荡的、不可导的、条件收敛的、需要用不同方法变形的 |
| 编程语言 | 一个逐步重构的小程序，每章加一个语言特性 |
| 日语 | 一段逐章加语法点的日记，每章回读一遍 |
| 乐理 | 一首逐章加深分析的曲子 |

### 2.2 概念台账（Concept ledger）

一个 JSON 文件登记**每个概念**：id、中英文、**首次定义章**。

规则三条：

1. 新章只能引用**已登记**的概念，或自己定义并登记；
2. 一个概念只能有一个首次定义章；
3. 改已发布章的术语 → 必须记变更，并列出受影响章（**语义冻结**）。

**这是唯一能自动发现漂移的机制**：写到第 10 章时引用了一个台账里没有的概念，脚本立刻报错。人工评审只能抽查，台账是全覆盖的。

### 2.3 复用矩阵

一张表：每个章 → 被哪几个章/项目复用。写大纲时就填，写正文时核对。

它把「我认为这章重要」变成「这章被这 6 处用到」。填不出来的章，删。

## 3. 可验证性工程

**一门教材的可信度，取决于它的断言有多少能被复跑验证。**

### 3.1 断言分级

| 级 | 判据 | 处理 |
| --- | --- | --- |
| A 机器可验 | 一条命令/一段代码能复算出答案 | 必须登记 `verify`，每次提交跑一遍 |
| B 证据可核 | 不能自动算，但人能按写明的步骤核对 | 标 `manual`，必须写具体 `evidence`（"看第 3 行"可以，"自己验证一下"不行） |
| C 只能人判 | 主观判断 | 尽量改写成 B；改不了就别写进正文当结论 |

**默认目标是把题推向 A**。做不到 A 时才用 B，并且 B 的 `evidence` 要写到"别人能照着核对"的程度。

### 3.2 题库格式（最小可用）

```json
{
  "id": "U00.2-01",
  "page": "u00-data-in-machine",
  "skills": ["hex"],
  "difficulty": 1,
  "minutes": 3,
  "answer": "c8",
  "verify": "python3 -c \"print(format(200,'02x'))\""
}
```

校验脚本：跑 `verify`，把 stdout 与 `answer` 比对。不一致就报错。
好处是**正文和答案键不可能不一致**——正文写错了，脚本会拦住。

### 3.3 学科适配：怎么把题变成可机验

| 学科 | 可机验的做法 |
| --- | --- |
| 安全/CTF | 直接跑命令，比对输出 |
| 数学 | `sympy` 化简/求值后比对；无解析解时用高精度数值比对（`mpmath`），并写出误差界 |
| 物理 | 量纲检查 + 特殊值代入 + 数值解 |
| 编程 | 跑测试用例 |
| 语言 | 固定语料上的标注一致性检查；或自我评分量表 + 抽查 |
| 乐理 | MIDI/音频特征值（音高、和弦识别）比对 |

数学特别注意：**别只验最终答案**。中间步骤也要给可核对的值（某一步的导数、某个代换后的积分），否则读者错了不知道错在哪。

## 4. 生产流水线

### 4.1 三级节奏

| 级 | 单位 | 产出 | 评审 |
| --- | --- | --- | --- |
| 节 | 15–25 分钟 | 一节正文 + 题号登记 | 自查 |
| 章 | 3–5 节 | 章首目标、章末术语表 + 自检 + 动手 | 跑校验脚本 + 提交 |
| Part | 3–5 章 + 1 项目 | 项目交付物 | **一次人工评审** |

章级只跑脚本，人眼留到 Part 级——因为 Part 末的项目会把前面章的漏洞一次性暴露。

### 4.2 开写前的 5 分钟：节表

不要写长篇大纲。写一张表，放在 `specs/<章ID>.md` 顶部：

```markdown
# U00 · 数据在机器里的样子
出口能力：判断任意文件是文本还是二进制，用 hex 列出前 16 字节
复用点：U10 U12 U20 U21 U23 U32
样本动作：7 个样本各列前 16 字节

| 节 | 锚点结果（读者做完会看到什么） | 机制一句话 | 速查 | 题 |
| --- | --- | --- | --- | --- |
| 0.1 | `file` 报 PNG，`xxd` 吐出 8950 4e47… | 类型是读者从头部字节推断的 | xxd 参数表 | U00.1-01 |
| 0.2 | `printf 'A' \| xxd` 得 41 | 16 = 2⁴，一位 hex 覆盖 4 位 | hex↔dec 表 | U00.2-01 |
```

**这张表就是漂移的第一个拦截点**：某节的锚点结果写不出来，说明这节没有可教的动作，当场删或并。5 分钟的投入，省一次返工。

### 4.3 逐节写作

1. 按四件套顺序写（锚点 → 机制 → 速查 → 题）；
2. **边写边跑**：写完一条命令立刻执行，把真实输出贴进去，不构造；
3. 题先登记到题库，再写 `<details>` 提示与答案；
4. 一节写完立刻 commit（`feat(U00.2): …`），章写完才推送。

### 4.4 校验脚本「随用生长」

**不要一开始写一堆检查项。** 检查项跟着课程长：

| 写到 | 才加上的检查 |
| --- | --- |
| 第 1 章 | 概念是否在台账登记；front matter 字段齐全 |
| 第 2 章 | 题号与题库双向一致；每条 `verify` 跑通 |
| 第 3 章 | 复用点 ≥3 |
| 第一个项目 | 项目覆盖：该 Part 的每章都被项目引用 |

脱离用例写的校验，一定过度设计。

### 4.5 推送策略（部署有配额时尤其重要）

- **commit 密，push 稀**。本地提交按节/章，推送按 **Part 边界**或用户明确要求。
- 静态站托管（Cloudflare Pages、Vercel、Netlify）每次推送都会触发一次构建，免费额度按次计。
- 合并前在本地跑一次构建（`hugo -D --gc --minify`）确认无误，别用云端构建当调试手段。

## 5. 写作规则（决定"保姆级"成不成立）

### 5.1 三条总则

1. **零搜索依赖**：读者不需要跳出页面查任何东西。概念当场定义，命令给全，输出给全，表就地给。
2. **原理优先**：给机制与推导。**禁用比喻**——比喻会让人以为懂了，实则没建立可操作的心智模型。
3. **可验证**：每个知识性断言配一条可复跑的命令与期望输出。

### 5.2 完整会话规则

每条命令必须给**输入与输出两块**：

```console
$ xxd -l 16 samples/S-01.png
00000000: 8950 4e47 0d0a 1a0a 0000 000d 4948 4452  .PNG........IHDR
```

- `$` 是提示符，读者不输入；
- 报错要给原文，并解释"这行报错在说什么"；
- 首次出现的命令要说明"在哪个窗口敲"；
- 不许 `...` 省略，除非同时给出完整版。

### 5.3 三种 inline 标记（替代笼统的「注意事项」）

```
> **易错**　90% 的人会写成 X，报错原文是 `Y`
> **约定**　业界默认这样做，不是硬性规定
> **实践**　实战里建议固定这个动作，能省时间
```

### 5.4 禁用词表

| 不要写 | 改成 |
| --- | --- |
| 「就像……」「好比……」 | 直接讲机制 |
| 「显然」「众所周知」 | 给出推导或删掉 |
| 「自己查一下」「见文末链接」 | 当场讲清；链接只作延伸 |
| 「理解 X」当目标 | 「给定 Y 能做出 Z」 |

## 6. 防漂移：6 条结构约束

比"多加评审环节"有效得多。评审只能事后抓，结构约束能事前禁。

| # | 约束 | 拦什么 |
| --- | --- | --- |
| 1 | **节表前置**：锚点结果写不出来就不写这节 | 没有可教动作的空节 |
| 2 | **概念台账**：只能引用已登记概念 | 语义被偷偷改 |
| 3 | **语义冻结**：已提交章的定义不改，只追加 | 前后章冲突 |
| 4 | **复用门槛**：章 ≥3 处复用，否则降为速查 | 知识堆积 |
| 5 | **贯穿样本**：新章若推翻旧章结论，立即暴露 | 理解被后续否定而没人发现 |
| 6 | **项目即回归测试**：项目做不出来就回头改章 | 一路往前写，越写越虚 |

**逐节产出时，漂移只可能发生在两个地方**：概念语义被偷改、依赖被凭空加。约束 2 和 3 正好各封一个。

## 7. 从零复刻：12 步清单

以新建一个「高等数学」教材站为例。

```text
1.  用三问（§0）确认学科适配
2.  定 Part 划分：能力阶层，3–7 个，每个一句「学完能独立完成什么」
3.  定章清单：20–30 章，每章填「复用点」列——填不出来的删
4.  选贯穿样本：一组固定函数/数据，写 build-corpus 与 verify-corpus
5.  建最小题库骨架：id / page / answer / verify
6.  写第 1 章的节表（5 分钟那张表）
7.  写完第 1 章（3–5 节），跑通校验脚本
8.  把校验脚本按 §4.4 长到"够用"，不多写
9.  写第 1 个 Part 的项目页，用它当回归测试
10. 人工评审一次（用 §8 的清单），决定格式要不要返工
11. 之后按 §4 量产：节 commit、章 push、Part 评审
12. 全部完成后补：索引页（按依赖自动生成学习顺序）、免责与来源页
```

前 6 步做完，再动笔写正文。**顺序错了就会返工**——第 7 步写正文时才发现第 3 步的章划分不对，代价是重写整章。

## 8. Part 级评审清单

一章写完只跑脚本。人眼评审一个 Part 一次，看这 7 类：

- [ ] **跨章一致性**：同一概念在不同章定义一致（对台账）；没有两章重复讲同一件事
- [ ] **贯穿样本**：本 Part 的样本动作已入档；新结论没推翻旧结论
- [ ] **能力达成**：随便挑一条「出口能力」，现在真能做出来
- [ ] **项目可做性**：项目所需章都已完成，没有隐形前置
- [ ] **保姆级**（抽 3 节粘贴即跑）：命令完整、输出一致、术语当场定义、无比喻
- [ ] **题与答案**：编号合规、折叠提示与答案齐全、机器可验的真能跑通、至少一题是反方向
- [ ] **工程**：校验脚本全绿、构建通过、路由正确

结论只写两种：通过 / 打回 + 具体条目 + 需要回头改的章。

## 9. 常见失败模式

| 失败模式 | 症状 | 拦它的约束 |
| --- | --- | --- |
| **分类学冒充课程** | 按学科分支排章（数学分代数/几何/分析），读者学完不会用 | §1.3 项目当回归测试 |
| **知识堆积** | 每章都对，合起来不会；删掉一半不影响能力 | §1.4 复用门槛 |
| **无螺旋** | 同一概念换个外壳读者就认不出来 | §2.1 贯穿样本 |
| **前置是假的** | 依赖边只是"主题相邻"，不是"缺了它第一步就做不下去" | 节表前置 |
| **时间估算靠编** | 没跑过一次就写"60 分钟" | 实测记录 |
| **断言靠猜** | 报错原文、数值、字节数看起来合理但是编的 | §5.2 完整会话 + 边写边跑 |
| **章太大** | 一章 2 小时，读者永远没有闭环感 | §1.1 节 15–25 分钟 |
| **常识当课上** | 查表内容单独成章，占掉注意力却不训练任何动作 | §1.4 复用门槛 |
| **校验过度设计** | 一开始写 4 个检查脚本，一半日后用不上 | §4.4 随用生长 |
