# 决策记录

按时间倒序。每条写「决定了什么 / 为什么 / 代价」。

## D-09 技能页用 `draft = true` 交付

- **为什么**：用户要审阅后再发布；草稿不进 `public/`，线上站不受影响。
- **代价**：需要在 `hugo -D` 下才能预览；发布前要逐页改 `draft = false`。

## D-08 题库用 JSON 而非 YAML

- **为什么**：`check-kb.py` 只依赖标准库（`json` + `tomllib`），不引入 PyYAML；WSL 里没装。
- **代价**：人工编辑时没有 YAML 的注释和多行字符串便利，已在 `kb/README.md` 说明字段。

## D-07 题目分「机器可验证」与「人工证据」两类

- **为什么**：编码/解码类题可以跑命令比对答案；文件类型判断题无法自动化，但可以要求写出可核对的事实。
- **代价**：`manual` 题的质量取决于 `evidence` 写得够不够具体。

## D-06 不转载题面，只链接 + 自写解法

- **原因**：版权归原作者；档案站改版会让单题链接漂移；而解法比题面更有教学价值。
- **代价**：读者需要点出去看题面（但解法、提示、复盘都在站内）。

## D-05 先技能页后项目页

- **原因**：用户指出「没有积累就做不动项目」，所以顺序必须是「先学单元、再挑精确匹配的题、最后用项目串联」。
- **代价**：早期上线的内容偏「零散知识点」，缺少成就感；靠项目页补。

## D-04 URL 用 `/s/` 与 `/proj/` 前缀

- **原因**：与旧文章的 `/p/` 区分，便于以后按类型做索引页。
- **代价**：`hugo.toml` 多两条 permalink 规则。

## D-03 课程不用固定 8 模块，而用「技能 + 依赖」

- **原因**：旧 8 篇是课程表气质；用户要的是「学完 X 立刻做 X 的题」。依赖图能自动排出顺序。
- **代价**：需要一个课程地图文档维护依赖与覆盖。

## D-02 站点独立成 `aistudy-blog` 仓库

- **原因**：用户要求与个人博客 `miaki-blog` 分开。
- **代价**：主题用子模块锁定在 `2f8b1be`（与博客同一 commit），保证渲染一致。

## D-01 技术栈 Hugo + Stack，不换 docs 主题

- **原因**：已部署、渲染稳定，换主题要重配，和「少在形式上花精力」冲突。
- **代价**：没有原生侧边栏导航，需要后续自己加索引页。
