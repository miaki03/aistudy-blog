# 写作规范（每页必须遵守）

## 三条总则

1. **保姆级**：读者不需要跳出页面搜索任何东西。概念当场定义，命令给完整，输出给完整。
2. **原理优先**：讲机制与推导。不允许用比喻代替解释。
3. **可验证**：每个知识性断言尽量配一条可复跑的命令与期望输出。

## 禁用与替换

| 不要写 | 改成 |
| --- | --- |
| 「就像……」「好比……」 | 直接讲机制 |
| 「这是 Base32 的地盘」 | 「这个字符集只包含 32 个符号，对应 5 位一组」 |
| 「`-` 是 `+` 的替身」 | 「Base64url 在字母表里用 `-` 替换 `+`、用 `_` 替换 `/`」 |
| 「万能钥匙」「门禁」「兔子洞」以外的比喻 | 直接陈述规则 |
| 「自己查一下」「见文末链接」 | 当场讲清；链接只作延伸 |
| 「显然」「众所周知」 | 给出推导或删掉 |

> 「兔子洞」「门禁」在 ARG 领域是**术语**，可以用；其他比喻一律替换成机制描述。

## 页面骨架（顺序固定）

```
+++
front matter（见下）
+++

## 读完能做什么              ← **1 条主目标**（可带 1–2 个子句），必须是「给定 X 能做 Y」
## 前置：需要先知道的N个概念   ← 只列本页真正用到的，当场定义
## 原理 / 算法                ← 推导向，不跳步
## 示例（至少 2 个，含一个反方向）
## 常见错误                   ← 贴真实报错原文 + 修法
## 跨平台 / 环境说明           ← 命令依赖什么环境
## 自检                       ← 3 题，概念层，可机验，折叠答案
## 动手                       ← 1–2 个，要交出东西（两层练习，对应 Review Questions / Programming Exercises）
## 本单元速查                 ← 本页用到的表就地放这里，不集中到附录
## 小结                       ← 5 行以内，回到「读完能做什么」
## 术语                       ← 本页的术语表，中文 / English / 定义
## 延伸                       ← 只放真正需要的出处
```

> 术语表与速查表**跟着单元走**，不设全局附录（C++ Primer 的每章 Glossary）。
> 真正的全局附录只有三个：术语中英对照、工具参数速查、报错速查。

> **为什么主目标只许 1 条**：3 条目标本身就是堆料的接口——写满 3 条等于承诺 3 个能力，80 分钟装不下，
> 结果每一条都变成"提了一句"。一章只承诺一件事，其余拆成下一章。

## 练习站优先（手熟型知识不自己造练习）

| 类型 | 判据 | 做法 |
| --- | --- | --- |
| 手熟型 | 知道怎么做之后，剩下的是练多少遍 | 指向 Bandit / picoCTF / CryptoHack 等免费站，正文给最短必要知识 + 打哪几关 + 为什么是这几关 |
| 结构化型 | 不解释就做不出来（判据、对照表、推导） | 自己写 |

引用练习站必须补上它缺的四样：**成体系的任务流、报错怎么读、中文直白解释、为什么是这个命令**。
细则见 `09-writing-brief.md` §5。

## 完整会话规则（零基础假设）

每条命令必须给出**输入与输出两块**，读者要能对照自己屏幕上出现了什么：

```console
$ xxd -l 16 samples/corpus/S-01.png
00000000: 8950 4e47 0d0a 1a0a 0000 000d 4948 4452  .PNG........IHDR
```

- `$` 表示提示符，不要读者输入；
- 报错要给原文，并写清「这行报错在说什么」；
- 首次出现的命令要说明「在哪个窗口输入」；
- 不许出现 `...` 省略，除非同时给出完整版。

## front matter 字段

```toml
+++
date = '2026-11-09T10:00:00+08:00'   # 必须早于构建时间，否则不渲染
draft = true                          # 未验收前一律 true
title = '…'
description = '…'                     # 一句话说清学到什么
slug = 'kebab-case'
chapter = 'S-B64'                     # 技能页 S-*，项目页 P*
stage = 1                             # 1 基础 / 2 进阶 / 3 实战
minutes = 70
prereq = ["S-BIN"]                    # 依赖的技能 ID
skills = ["base64"]                   # 本页覆盖的技能标签
problems = ["B64-01"]                 # 必须存在于 kb/problems.json
+++
```

## 练习与答案规则

**两层练习**（缺一层不算完成）：

| 层 | 数量 | 性质 | 对应 |
| --- | --- | --- | --- |
| 自检 | 3 题 | 概念层，可机验，一问一答 | C Primer Plus 的 Review Questions |
| 动手 | 1–2 个 | 要交出东西（一段输出、一个脚本、一个判定） | 的 Programming Exercises |

共同规则：

- 每问必须有 **提示** 与 **答案** 两个 `<details>`；
- 答案里附一条可复跑命令；
- 提示是**层层递进**的 1–3 条，不是「再想想」；
- 题号写进 front matter 的 `problems`，并登记到 `kb/problems.json`；
- 机器可验证的题必须有 `verify` 命令；不能机器验证的标 `manual: true` 并写 `evidence`；
- ≥1 题必须是**反方向**（编码页要有解码题，识别页要有「这不是 X」的判别题）。

## 长度参考（预警，不是门槛）

| 页型 | 正文字数 | 时长 |
| --- | --- | --- |
| 单元（概念型） | 2000–2800 | 50–80 分钟 |
| 单元（工具型） | 1500–2500 | 40–70 分钟 |
| 单元（含练习站指引） | 1200–2000 | 40–60 分钟 |
| 项目页 | 1000–2000 | 150–240 分钟 |

**超出上限不自动拆章。** 像设计函数一样：不能因为一条必要的代码让函数超过 30 行就硬拆成两个——
拆开的代价是读者要在两个地方拼回一个概念。

判断标准只有一条：**删掉它，读者下一步就做不出来。** 不是「它很重要」，是「删了会卡」。
必要则保留，并在 `specs/<章>.md` 写明超出理由；不必要才砍，砍的优先顺序：
删元话语 > 删重复示例 > 删铺垫 > 合并节。
